CT 体数据可视化的第一道门槛不是“把图片显示出来”，而是确认每个像素值和每张切片在体数据中代表什么。本文结合 [CT3D](https://github.com/Lketchum/CT3D) 的现有 MATLAB 与 C# 实现，梳理 DICOM 到 HU 的输入链路。

<!-- more -->

## 背景

DICOM 序列看起来像一组灰度图，但直接按文件名堆叠会埋下三类问题：

1. 文件顺序不一定等于空间顺序；
2. 行列像素间距和层间距可能不同；
3. 存储像素值通常还要经过 slope/intercept 才能得到 HU。

如果输入体的顺序、尺度或数值语义错误，后续 MPR 即使代码能运行，也只是在稳定地产生错误结果。

## 原理

### 从存储值到 HU

常用线性变换为：

`HU = storedValue × RescaleSlope + RescaleIntercept`

HU 体应作为后续计算的基础数据。窗宽窗位不是再次修改 HU，而是把一个 HU 区间映射到显示灰度。给定窗位 `L` 和窗宽 `W`，核心思想是把 `[L - W/2, L + W/2]` 内的值线性映射，区间外截断。边界定义和整数取整需要在两套实现中保持一致。

### 排序与空间

序列组织应优先依据可用的空间位置和方向信息；序列号可以作为数据条件受限时的辅助，但文件名不是可靠的医学空间依据。排序完成后还要检查切片位置是否单调、间距是否稳定，以及是否存在缺层或重复层。

`PixelSpacing` 描述图像平面内两个方向的物理采样间隔。第三个方向应从切片几何推导或读取合适的间距信息。把 spacing 全部当成 1，会让冠状面和矢状面的比例失真。

## 实现映射

CT3D 的 MATLAB 线包含 DICOM→HU、窗宽窗位和三平面 MPR，适合逐步观察中间矩阵。C# .NET 8 WPF 线包含 DICOM 序列读取、HU 和正交 MPR，负责把输入、领域数据和显示流程工程化。

C# 当前支持范围是：

- 单帧/文件；
- 8/16-bit 单色像素；
- 非压缩 DICOM。

这意味着多帧对象、彩色数据和压缩传输语法不能因为“也是 DICOM”就默认可用。实现入口应先检查能力边界，再进入像素解码。

数据职责可以按以下顺序理解：

1. 读取必要标签和原始像素；
2. 建立序列顺序与 spacing；
3. 按像素表示方式解释 8/16-bit 存储值；
4. 使用 slope/intercept 生成 HU 体；
5. MPR 从 HU 体取样；
6. 窗宽窗位只在输出显示阶段应用。

## 验证方法

- **标签级检查**：记录用于排序、spacing 和 HU 变换的标签，确认缺失值处理不是静默猜测。
- **可预测像素**：选取已知存储值与 slope/intercept 的小样本，手算 HU 并对照程序输出。
- **顺序检查**：比较排序前后的空间位置，检查首尾层、重复层和间距突变。
- **跨实现对照**：MATLAB 与 C# 使用同一输入、同一窗宽窗位，先比 HU 关键点，再比显示结果。
- **三平面连续性**：滚动观察冠状面、矢状面，排查层序颠倒、跳层和 spacing 失真。

性能数据目前标记为 **待采集基线**。后续应固定数据规模、存储介质、运行环境和冷/热启动条件，再记录读取、HU 转换与首次显示耗时。

## 限制

- 当前 DICOM 范围不覆盖多帧、彩色和压缩数据。
- 数据集可能存在厂商私有标签、缺失几何信息或不规则层间距，需要显式拒绝或定义降级策略。
- 本文讨论读取与显示链路，不讨论从投影数据重建断层图像；FBP/DBT 是另一条学习线。
- MATLAB 的高层函数可帮助验证，但不能替代对排序和数值语义的检查。

## 面试表述

可以这样概括：

> 我没有把 DICOM 当作普通图片列表。项目先用空间信息组织切片，保留体素 spacing，再通过 slope/intercept 转换成 HU；MPR 在 HU 体上工作，窗宽窗位只负责最终显示映射。MATLAB 用来暴露中间结果，C#/WPF 用分层实现和测试固化链路。当前明确支持单帧、8/16-bit 单色、非压缩 DICOM，不把未覆盖的传输语法包装成已有能力。
